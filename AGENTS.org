* What this repo is

Clojkstra is a *ClojureScript + re-frame starter template*.
It is not a one-off app — it is a reusable scaffold designed to be cloned and customised into new projects.
Every file is labelled either ~[FRAMEWORK]~ (keep it, modify it carefully) or ~[DEMO]~ (example content, safe to delete).
Must read until end! If you're AI, load all this entire file into context.
* Language and runtime

- *ClojureScript* — all source files are =.cljs= under =src/clojkstra/app/=
- *shadow-cljs* — the build tool; config is =shadow-cljs.edn=
- *Bun* — the JS runtime and package manager. Never use =npm= or =node=. Always use =bun= or =bunx=.
- *Clojure CLI* (=clojure= / =clj=) — used by shadow-cljs for classpath resolution from =deps.edn=
- *re-frame* — all state lives in a single =app-db= map; mutations happen only through registered event handlers; views read only through subscriptions
- *just* use justfile for easy seamless cli operations

* OpenSpec Workflow and VSDD

You must use *OpenSpec* for complex tasks.
If a task is non-trivial, spans multiple files, changes behaviour, adds a feature, modifies architecture, or will likely take longer than a quick edit, create an OpenSpec change first.

The Problem

AI coding agents tend to fail in predictable ways:

- Volatile memory — goals drift as the context window fills
- Hidden assumptions — implementation details appear that were never agreed on
- Untracked scope — behavior changes without a durable spec trail
- Weak review surfaces — code lands before the contract is clear

The Solution: OpenSpec Change Workflow

For every meaningful change, create an OpenSpec change under =openspec/changes/hange-id>/=.
OpenSpec’s core workflow is based on *propose*, *explore*, *apply*, and *archive*, and its change artifacts center on =proposal.md=, =tasks.md=, optional =design.md=, and spec delta files under =specs/=.[web:17][web:20][web:21][web:24][web:27]

Use this structure:

#+BEGIN_SRC text
openspec/
  specs/                       source-of-truth capabilities/specs
  changes/
    hange-id>/
      proposal.md              why this change exists, scope, impact
      tasks.md                 numbered implementation checklist
      design.md                optional technical design for larger work
      specs/
        apability>/
          spec.md              ADDED/MODIFIED/REMOVED requirement deltas
#+END_SRC

Rules

1. *Start with a proposal.* Describe the problem, desired behavior, scope, and impact in =proposal.md=. Do not start implementation first.[web:19][web:20][web:24]
2. *Write the spec delta.* Record the contract change in =specs/.../spec.md= using explicit ADDED, MODIFIED, or REMOVED requirements.[web:20][web:24]
3. *Use design.md when needed.* If the task touches architecture, multiple systems, Tauri integration, routing, state shape, or verification strategy, add =design.md= before implementation.[web:21][web:24]
4. *Break work into tasks.* Use =tasks.md= as the authoritative checklist. Keep tasks concrete, reviewable, and sequential.[web:20][web:21][web:24]
5. *Apply only after review.* Implementation follows the approved proposal, design, and spec delta. Update task checkboxes as work completes.[web:19][web:21][web:24][web:26]
6. *Archive when done.* After the change is complete, archive it so the delta specs are merged into =openspec/specs/= and the change folder moves into the archive history.[web:21][web:24][web:26]

The Loop

1. Create an OpenSpec change ID and scaffold =proposal.md=, =tasks.md=, optional =design.md=, and delta specs.[web:20][web:24]
2. Review the proposal and spec delta until the intended behavior is explicit.[web:19][web:24]
3. Implement strictly from =tasks.md= and update the checklist as each item is completed.[web:21][web:24]
4. Archive the change so the living spec stays synchronized with the codebase.[web:21][web:24]

OpenSpec + VSDD

OpenSpec is the workflow shell around VSDD, not a replacement for rigor.
Use OpenSpec to store the contract and task trace, then execute VSDD inside that change.

Map VSDD onto OpenSpec like this:

- *Phase 1 — Spec Crystallization* → =proposal.md= + spec delta + optional =design.md=
- *Phase 2 — Test-First Implementation* → tasks in =tasks.md= written and executed in strict TDD order
- *Phase 3 — Adversarial Refinement* → review the proposal, tests, and implementation against the delta spec
- *Phase 4 — Feedback Integration Loop* → update proposal/spec/tasks before continuing
- *Phase 5 — Formal Hardening* → run proofs, fuzzing, mutation testing, and audits against the implemented change
- *Phase 6 — Convergence* → archive only when spec, tests, implementation, and verification agree

OpenSpec discipline for this repo

- For anything beyond a tiny local refactor, create an OpenSpec change first.
- If behavior changes, the spec delta must change too.
- Do not treat =tasks.md= as notes. It is the implementation checklist.
- Do not skip archiving completed work, because archived deltas update the living source-of-truth specs.[web:21][web:24]
- Do not implement code that is not justified by the proposal, spec delta, or tasks list.

When to require =design.md=

Create =design.md= when any of the following are true:

- The change introduces a new Tauri command
- The change adds or reshapes =app-db=
- The change affects routing, effects, or cross-page state flow
- The change introduces a new capability that needs verification strategy
- The change spans both Rust and ClojureScript layers
- The change is ambiguous enough that implementation would otherwise involve guessing

Validation mindset

Before implementation, verify:

- The proposal states *why* the change exists
- The spec delta states *what behavior changes*
- The design states *how the architecture will support it*, when needed
- The tasks state *what to do next* in executable order

Only then begin code changes.

* Tauri integration

** Architecture

Clojkstra runs as a Tauri v2 desktop app.  The architecture is a strict two-layer split:

- *Frontend* — the existing ClojureScript + re-frame SPA, compiled by shadow-cljs into =docs/cljs-out/main.js= and served from =docs/index.html=.  In dev mode Tauri points its webview at the shadow-cljs dev server (=http://localhost:8080=).  In release mode it bundles =docs/= directly.
- *Backend* — a minimal Rust host process in =src-tauri/=.  It owns the native window, OS integrations, and any privileged operations (filesystem, shell, notifications, etc.) that the webview cannot do.  The frontend communicates with it exclusively through Tauri commands and events.

** Calling Tauri from ClojureScript

Use =js/window.__TAURI__= only through a registered effect handler in =effects.cljs=.  Never call Tauri APIs directly from a view or event handler.

Example effect handler pattern:

#+BEGIN_SRC clojure
;; effects.cljs
(rf/reg-fx
  ::invoke-tauri
  (fn [{:keys [command args on-success on-error]}]
    (-> (js/window.__TAURI__.core.invoke command (clj->js (or args {})))
        (.then  #(when on-success (rf/dispatch (conj on-success (js->clj % :keywordize-keys true)))))
        (.catch #(when on-error  (rf/dispatch (conj on-error  (.-message %))))))))
#+END_SRC

Dispatch it from a =reg-event-fx= handler:

#+BEGIN_SRC clojure
;; events.cljs
(rf/reg-event-fx
  ::my-native-action
  standard-interceptors
  (fn [{:keys [db]} [_ payload]]
    {:db (assoc db :loading? true)
     ::effects/invoke-tauri {:command   "my_command"
                             :args      {:payload payload}
                             :on-success [::my-native-action-ok]
                             :on-error   [::my-native-action-err]}}))
#+END_SRC

** Adding a new Tauri command

1. Define the Rust function in =src-tauri/src/lib.rs= with the =#[tauri::command]= attribute.
2. Register it in the =.invoke_handler(tauri::generate_handler![...])= call in the same file.
3. Add a capability entry in =src-tauri/capabilities/= if the command needs elevated permissions.
4. Add a =::invoke-tauri= effect call (see above) — never call =js/window.__TAURI__= inline.
5. Add the new event/sub/db key following the normal re-frame conventions.

** CSP

The Content Security Policy is set in =src-tauri/tauri.conf.json= under =app.security.csp=.
If you add a new external resource (CDN, font host, etc.) you must add its origin to the relevant CSP directive.  Do not set =csp= to =null= — that disables all CSP protection.

** What NOT to do (Tauri)

- Do not call =js/window.__TAURI__= directly from views or re-frame event handlers.  Route all native calls through a =reg-fx= effect in =effects.cljs=.
- Do not add heavy business logic to =src-tauri/src/lib.rs=.  Keep Rust commands thin: validate input, call a library or OS API, return a result.
- Do not edit =src-tauri/build.rs= — it is generated boilerplate required by Tauri.
- Do not commit =src-tauri/target/= — it is =.gitignore='d and can be several gigabytes.
- Do not use =tauri::Manager= to reach into the webview and mutate DOM state.  All UI state flows through re-frame.

* Version control — jujutsu (jj)

This repo uses *jujutsu* (=jj=), not plain git. Key differences:

- The *working copy is always a change*. You never need =git add=. Every file edit is automatically part of =@= (the current change).
- Use =jj describe -m "msg"= to set the commit message of the current change without finalising it.
- Use =jj commit -m "msg"= to finalise =@= and open a new empty child change.
- Use =jj status= / =jj diff= instead of =git status= / =git diff=.
- Never run =git commit=, =git add=, or =git checkout= directly.
- The primary bookmark is =main=. After committing, advance it with: =jj bookmark set main --revision @-=
- All of this is wrapped in =just= recipes — prefer =just commit=, =just snap=, =just ship= over raw =jj= calls.

* re-frame conventions

Follow these rules strictly — they are the architecture of this project:

1. *No side effects in views.* Views call =rf/dispatch= and =@(rf/subscribe …)= only. They never call =js/fetch=, mutate atoms outside Reagent, or touch =js/localStorage= directly.
2. *No direct db reads in views.* Views read app-db exclusively through named subscriptions in =subs.cljs=. Never pass =db= into a component.
3. *Events mutate db; effects reach outside.* =reg-event-db= for pure db updates. =reg-event-fx= when a side effect is also needed. Side effects go through registered =reg-fx= handlers in =effects.cljs=.
4. *Layer-2 subscriptions extract; layer-3 subscriptions derive.* A layer-2 sub reads a raw slice of =db=. A layer-3 sub uses =:<-= to depend on layer-2 subs and computes a derived value. Never skip layers.
5. *All new state goes in =db.cljs= first.* Add every new top-level key to =default-db= with a comment explaining its purpose before writing events or subs that reference it.
6. *Keyword namespacing.* Event and subscription keywords use =::= in their own namespace (=::initialize-db= in =events.cljs=) and alias-qualified =::events/initialize-db= from other namespaces. Never use plain unnamespaced keywords for re-frame registrations.
7. =standard-interceptors= must be attached to every =reg-event-db= / =reg-event-fx= call. See =events.cljs=.

* Adding a new page

1. Create =src/clojkstra/app/pages/my_page.cljs= with =(defn page [] …)=
2. Add a route in =routes.cljs= → =app-routes=: ="my-page" :my-page=
3. Require the page in =views.cljs=; add a =case= branch in =page-for-route=
4. Add ={ :handler :my-page :label "My Page" }= to =nav-links= in =views.cljs=
5. Seed any new state in =db.cljs= under a clearly named top-level key
6. Add events in =events.cljs=, subscriptions in =subs.cljs=

* Adding a new UI component

Add it to =src/clojkstra/app/components/ui.cljs=.

- Pure function of props — no =rf/subscribe= calls inside =ui.cljs=
- Accept an optional =:class= prop on every component for caller overrides
- Document the prop signature in the docstring
- If the file grows large, split into =components/forms.cljs=, =components/data_display.cljs=, etc. and re-export from =ui.cljs=

* Adding a new effect handler

Add it to =src/clojkstra/app/effects.cljs= using =rf/reg-fx=.

- The handler body must be a pure side-effect function — no =db= reads
- Document the usage shape in the docstring
- Call it from =reg-event-fx= via the effects map, never directly from a view

* Feature flags

Feature flags live in =db.cljs= under =:config :features=.
Gate unfinished work behind a flag. Check in a view with:

#+BEGIN_SRC clojure
@(rf/subscribe [::subs/feature-enabled? :my-flag])
#+END_SRC

Toggle at runtime:

#+BEGIN_SRC clojure
(rf/dispatch [::events/toggle-feature :my-flag])
#+END_SRC

* What NOT to do

- Do not run =npm=, =node=, =yarn=, or =npx=. Use =bun= / =bunx= only.
- Do not run =git commit=, =git add=, =git checkout=. Use =jj= / =just=.
- Do not edit files in =docs/cljs-out/= — they are generated.
- Do not put business logic in =views.cljs= or any =pages/= file. Views dispatch and subscribe; logic lives in events, subs, and effects.
- Do not add new top-level deps to =deps.edn= without checking that they are FOSS-licensed and have a ClojureScript-compatible build.
- Do not break the ~[FRAMEWORK]~ files to fix a ~[DEMO]~ problem. Delete the demo, don't patch around it.

Run:

just ci
